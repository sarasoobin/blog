## 왜 만들었나

기존 캘린더 앱은 **중요일정과 자잘한 일정을 같은 칸에 같은 크기로** 적습니다.
그러다 보니 정작 중요한 일정이 자잘한 할 일 사이에 묻혀서 눈에 안 들어옵니다.

이 앱은 **적는 곳을 아예 분리**해서 이 문제를 풀었습니다.

| | 어디에 적나 | 무엇을 적나 |
|---|---|---|
| 🔴 **중요한 일정** | 월간 페이지의 달력 칸 | 시험, 마감일, 약속 |
| ⚪ **자잘한 할 일** | 주간 페이지의 요일 칸 | 목데이터 연결, 강의 듣기 |

주간 페이지 각 칸 맨 위에는 그 날 달력에 적어둔 중요한 일정이 **색 띠**로 따라옵니다.
"오늘 뭐 하지"를 볼 때 "이번 주에 뭐가 걸려 있지"가 같이 보이게 하려는 의도입니다.

![주간 페이지](https://raw.githubusercontent.com/sarasoobin/yellow-planner/main/docs/screenshot-week.png)

컨셉은 **노란 표지의 아날로그 공책 한 권**입니다. 앱을 쓰는 게 아니라 다이어리를
펼치는 느낌을 목표로 했습니다. 오른쪽에 표지 · 1월~12월 · 메모 인덱스 탭이 붙어 있고,
로고는 `正` 한 글자입니다. 다섯 획을 세는 표시라, 실제로 완료 개수를 세는 데 씁니다.

![표지](https://raw.githubusercontent.com/sarasoobin/yellow-planner/main/docs/screenshot-cover.png)

## 기술 스택과 고른 이유

| 분류 | 사용 기술 | 왜 |
|---|---|---|
| 프레임워크 | Next.js 16.2 (App Router) | Server Actions로 API 라우트를 안 만들어도 되고 Vercel 배포가 무설정 |
| UI | React 19.2, TypeScript 5, Tailwind CSS 4 | 디자인을 직접 하므로 유틸리티 방식이 가장 빠름. 색은 `@theme` 토큰 한 곳에서 관리 |
| 백엔드 | Supabase (PostgreSQL + Auth) | 무료 티어로 Postgres·인증·RLS를 한 번에. **인가를 DB 계층에 두려면 RLS가 필요했음** |
| 검증 | Zod 4 | Server Action에 들어오는 값은 전부 남이 보낸 것이라 서버에서 다시 검사 |
| 걸러내기 | sanitize-html | 서식을 담으려고 HTML로 저장하므로 저장 직전에 허용 목록으로 거름 |
| 날짜 | date-fns 4 | 주/월 경계 계산. `toISOString()`은 UTC로 바꿔 하루 밀리므로 쓰지 않음 |

**의도적으로 안 쓴 것:** 전역 상태 라이브러리(React 내장으로 충분), Prisma(Supabase
클라이언트로 충분), 리치 텍스트 에디터 라이브러리(종이 느낌을 내려면 결국 다
뜯어고쳐야 해서 직접 만드는 편이 빨랐음).

## 아키텍처

```
브라우저 (PaperBlock, contenteditable)
   │  칸에서 손 떼면 저장
   ▼
proxy.ts — 세션 갱신 · 보호 라우트
   ▼
Server Action — saveBlock / saveNote
   ▼
Zod 검증 → sanitize-html 로 거르기
   ▼
Supabase PostgreSQL
   ▼
RLS — 본인 행만 오간다
   │  revalidatePath 로 화면 다시 그리기
   ▼
브라우저
```

API 라우트가 없습니다. 폼이 Server Action을 직접 부르고, 그 안에서 검증 → 걸러내기 →
저장까지 끝냅니다. **인가는 앱이 아니라 DB가 합니다.**

## 기술적으로 신경 쓴 것

### 1. 인가를 앱이 아니라 DB에 뒀습니다

앱 코드에서 `user_id`로 거르지 않습니다. PostgreSQL의 Row Level Security가 DB
레벨에서 본인 데이터만 오가도록 강제합니다.

```sql
create policy "본인 항목만" on public.items for all
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);
```

앱 코드에 버그가 있어도 남의 데이터는 새어나가지 않습니다. 다른 사람의 id로 삭제를
시도하면 에러가 아니라 **0건 처리**로 끝납니다.

`(select auth.uid())`로 감싼 것은 행마다가 아니라 쿼리당 한 번만 평가시키기 위한
것입니다.

**교차 검증했습니다.** 계정 A로 표지·달력·주간·메모를 채운 뒤 계정 B로 들어가 네
화면이 모두 비어 있는 것을, 다시 A로 돌아와 그대로 남아 있는 것을 확인했습니다.
화면에서 숨긴 것이 아니라 서버 응답에 애초에 들어 있지 않습니다.

### 2. 테이블 하나로 네 개의 화면을 굴립니다

표지 · 월간 왼쪽 칸 · 달력 칸 · 주간 요일 칸은 **"날짜에 묶인 짧은 글 + 체크"** 라는
같은 구조입니다. 테이블을 나누는 대신 `kind` 컬럼 하나로 구분했습니다.

| `kind` | 화면 | `date`에 저장하는 값 |
|---|---|---|
| `year` | 표지 | 그 해 1월 1일 |
| `month` | 월간 왼쪽 칸 | 그 달 1일 |
| `event` | 달력 칸 (중요 일정) | 실제 날짜 |
| `task` | 주간 요일 칸 (자잘한 할 일) | 실제 날짜 |

덕분에 편집기 한 벌(`PaperBlock`)과 Server Action 하나(`saveBlock`)가 네 화면을
전부 담당합니다. 새 화면이 생겨도 `kind`만 늘리면 됩니다.

### 3. 줄 목록이 아니라 "종이 한 면"으로

처음에는 "할 일 하나 = DB 한 행"이었습니다. 그런데 종이 다이어리는 그렇게 안 씁니다.
마구잡이로 쓰고, Enter로 줄을 바꾸고, 필요한 줄에만 네모를 그립니다.

그래서 **한 칸이 통째로 한 행**이 됐습니다. 체크박스도 컬럼이 아니라 글자(`☐`/`☑`)로
글 안에 들어갑니다. 줄 앞이든 문장 중간이든 아무 자리에나 그릴 수 있습니다.

대가로 글을 HTML로 저장해야 했고, 그래서 저장 직전에 `sanitize-html`로 허용 목록에
없는 태그와 style을 전부 걸러냅니다. 붙여넣기는 글자만 받습니다.

### 4. 화면에 그리는 것과 저장하는 것을 나눴습니다

체크 표시 · 취소선 · 밑줄은 **글에 저장하지 않습니다.** 사실만 저장하고
(`☑`이라는 글자, `text-decoration: underline`) 보이는 줄은 자리를 재서 그립니다.

체크는 글 안의 한 글자라서 **그 글자만 빨갛게 하거나 키울 수가 없기** 때문입니다.
CSS로는 글자 하나를 집을 수 없습니다. 그래서 글자는 그대로 두고 그 위에 색연필 획을
그립니다. 네모를 넘어가도 둡니다 — 종이에 그으면 원래 그렇습니다.

### 5. 핸드폰에서는 다르게 만들었습니다

![핸드폰 주간 페이지](https://raw.githubusercontent.com/sarasoobin/yellow-planner/main/docs/screenshot-mobile.png)

주간의 7칸을 375px 화면에 가로로 우겨넣으면 한 칸이 45px가 됩니다. 글자 두 자
들어갑니다. 그래서 **세로로 쌓습니다.**

달력도 마찬가지였습니다. 실제로 재보니 375px에서 한 칸이 43px, 글자가 놓이는 자리는
34px였습니다. 13px 한글이 한 줄에 두세 자 들어가서 "과제 마감 23:59"가
`과제 마 / 감 23:5 / 9`로 잘렸습니다. **글자 크기를 줄여도 나아지지 않는 넓이**라
칸에서 글자를 빼는 것 말고는 길이 없었습니다.

폰에서는 달력을 한눈에 보는 용도로만 씁니다 — 날짜 + 색 띠 + 할 일 개수 점. 날짜를
누르면 달력 바로 아래에서 그 날을 적습니다. 종이 다이어리의 작은 월간 표와 같은 쓰임새입니다.

## 오래 걸린 문제 세 가지

포트폴리오에서 제일 하고 싶은 이야기입니다. **어떻게 잡았는지**가 남았습니다.

### 문제 1 — 적던 글이 자꾸 처음 내용으로 되돌아갔다

`/`를 칠 때마다 방금 친 글자가 사라지고 커서가 튀었습니다. **세 번을 추측으로
고쳤는데 다 빗나갔습니다.** Playwright로 실제 크롬을 계측하고 나서야 잡혔습니다.

React 19는 prop이 바뀌었는지 값이 아니라 **참조**로 판단합니다.

```js
if (nextProp !== lastProp) setProp(...)   // react-dom updateProperties
```

`dangerouslySetInnerHTML={{ __html: 문자열 }}`은 매 렌더마다 새 객체를 만듭니다.
문자열이 같아도 참조가 다르니 **매번 `innerHTML`을 다시 써넣고 있었습니다.**
그래서 다시 그려질 때마다 적고 있던 글이 통째로 초기값으로 되돌아갔습니다.

계측 증거: 편집기 노드는 그대로인데(remount 아님) 자식 11개가 통째로 교체
(added 11 / removed 11)되고 내용이 원본으로 복귀.

객체 자체를 붙들어 참조를 불변으로 만들어 해결했습니다.

> **배운 것 — 추측으로 세 번 고치느니 한 번 재는 게 빠릅니다.**

### 문제 2 — "4줄 이상 쓰면 저장이 안 된다"

재현하는 데 제일 오래 걸렸습니다. 실제 크롬으로 3·4·5·8줄, 자동 줄넘김, 폰 크기,
적고 바로 링크 클릭까지 다 해봤지만 **전부 저장됐습니다.**

원인은 코드가 아니라 **데이터베이스에 옛 200자 제약이 남아 있던 것**이었습니다.
스키마 파일에서는 5000자로 늘렸는데 그 파일을 Supabase에서 다시 실행하지 않았습니다.
제 시험 글자가 짧아서("하나/둘/셋/넷") 200자를 안 넘겼던 것입니다.

길이로 재고 나서 확정했습니다.

| 적은 글자 | 저장됨 |
|---|---|
| 150자 | 150자 ✓ |
| 190자 | 190자 ✓ |
| 210자 | 190자 (옛것) ✗ |

> **배운 것 — 앱과 DB는 따로 배포됩니다. 코드를 아무리 올려도 DB 설정은 안 바뀝니다.**

### 문제 3 — 로컬에서는 안 보이던 버그

"스티커 움직임이 이상하다"는 제보를 받고 제 컴퓨터에서 재봤는데 멀쩡했습니다.
놓는 자리를 0.12초 간격으로 8번 재도 값이 안 흔들렸습니다.

**배포된 서버에서 재보니 확실히 보였습니다.** 끌던 자리 (-3, 37)에서 손을 떼자마자
(595, 370)으로 되돌아갔다가, 저장이 끝난 뒤에야 (-3)으로 갔습니다.

원인은 서버 왕복 시간이었습니다. 손을 떼면 서버에 저장하는데 그 답이 올 때까지
화면이 **원래 자리를 보여주고 있었습니다.** 로컬은 왕복이 50ms라 눈에 안 띄었고,
배포 서버는 그보다 훨씬 길어 뒤로 튀는 게 보였던 것입니다.

놓은 자리를 화면이 먼저 붙들고 저장은 뒤따르게 고쳤습니다. 검증은 **저장을 일부러
1.5초 늦춰놓고** 했습니다 — 12번 재는 동안 자리가 그대로였습니다.

> **배운 것 — 로컬에서 안 보이는 문제가 있습니다. 느린 왕복을 흉내내서 재야 합니다.**

## 어떻게 검증했나

3일짜리 계획이라 테스트 프레임워크는 넣지 않았습니다. 대신 **Playwright로 실제
크롬을 띄워** 확인했고, 화면에서 실제로 벌어지는 일만 증거로 인정했습니다.

| 무엇 | 결과 |
|---|---|
| 빈 화면 · 로딩 · 에러 화면 | 16/16 |
| 형광펜 · 밑줄 · 취소선 | 16/16 |
| 마크다운 제목, 체크 표시 | 각 6/6 |
| 폰 월간 페이지 | 12/12 |
| 스티커 붙이기 · 옮기기 · 크기 | 6/6, 5/5, 4/4 |

시험은 데모 계정의 **2029~2030년 날짜**에서 했습니다. 실제로 쓰는 달을 안 건드리려는
것이고, 끝나면 지웠습니다.

`npm run build` 경고 0, `tsc`·`eslint` 0으로 유지하고 있습니다.

## 알면서 안 한 것

무엇이 부족한지는 알고 있습니다. 3일 안에 넣기에는 시간 대비 효용이 낮다고 판단한
것들입니다.

- **테스트 코드** — 지금은 Playwright를 손으로 돌립니다. 주/월 경계 계산부터 단위
  테스트로 묶는 것이 우선입니다
- **동시 편집 충돌 처리** — 두 기기에서 같은 칸을 열어두면 나중에 저장한 쪽이 앞의
  것을 조용히 덮어씁니다. `updated_at` 비교가 필요합니다
- **오프라인 지원** — 인터넷이 끊기면 저장이 실패합니다. 다이어리는 지하철에서 펴는
  물건이라 이게 제일 아쉽습니다
- **되돌리기(Undo)** — 형광펜을 잘못 칠하면 같은 자리를 다시 긁어 지우는 것이 유일한
  방법입니다

## 느낀 점 — 디자이너와 기획이 왜 있는지 체감했다

이 프로젝트를 하면서 가장 크게 남은 건 기술이 아니었습니다.

### 요구사항의 품질이 곧 결과의 품질이었다

AI가 코드를 아무리 잘 짜도, 제가 준 요구사항이 흐릿하면 결과물은 계속 제 기대와
어딘가 달랐습니다. 그리고 **제가 직접 확인하지 않으면** 기대와 전혀 다른 무언가가
만들어져 있었습니다.

간단하다고 생각한 플래너인데도 그랬습니다. "형광펜을 초록으로" 라고 했다가 세 색이
필요해졌고, "별표를 사람이 그린 것처럼" 이라고 했다가 가운데 선이 있는 별이어야
한다는 걸 나중에야 말했습니다. 체크 표시 크기는 키웠다가 줄였다가 다시 처음으로
돌아갔습니다. **명확한 요구사항이 없으면 같은 작업을 몇 십 번 반복하게 된다**는 걸
몸으로 알았습니다.

요즘은 AI 시대라 딸깍 한 번이면 웹이 짠 하고 만들어진다고 생각하는 사람이 많습니다.
직접 해보니 아니었습니다. AI가 코드를 잘 짜는 것과 별개로, **인간이 내놓는 요구사항의
품질**이 결과를 갈랐습니다.

### AI를 잘 쓰려면 내가 알아야 한다

AI를 잘 활용하려면 지금 내가 하는 것에 대한 전반적인 이해도가 높아야 한다는 걸
깨달았습니다.

그동안 AI로 코드를 짤 때 별 문제가 없었던 이유도 알았습니다. **이미 디자이너와
기획팀, 다른 파트에서 요구사항을 명확히 정해서 줬기 때문**이었습니다. 그 단계를
직접 해보니 간단한 웹 하나에도 파트별로 주고받아야 하는 요구사항이 이렇게 많다는
걸 알게 됐습니다.

### "사람이면 이게 더 편하겠지"는 아직 사람의 몫이었다

계속 AI에게 부탁하다가, 어떤 화면을 보고 "사람이면 이렇게 구성하는 게 당연히 더
편하겠지" 라는 생각을 제가 먼저 한 순간이 있었습니다. 그때 **이게 AI와 인간의
차이구나** 싶었습니다.

AI가 인간을 대체한다는 말이 많지만, 이런 걸 보면 절대 못 할 것 같습니다.
**모든 웹은 인간을 위해 만들어지는데, 인간이 느끼는 편리함을 AI가 파악하기에는
아직 무리가 있어 보입니다.**
